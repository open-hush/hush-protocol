## Devices — HMAC-SHA256

### Header format

```
Authorization: HMAC keyId=<device-id>,signature=<hex>,ts=<unix-seconds>
```

- `keyId` — the device UUID. Baked into NVS at factory along with the device serial and secret.
- `signature` — lowercase hex of `HMAC_SHA256(secret, canonical-request)`.
- `ts` — request creation time in seconds since the Unix epoch.

Parameters are comma-separated. Whitespace around the commas is ignored. Order is not significant. A missing or malformed header returns `401 unauthorized`.

### Canonical request

The string fed to `HMAC_SHA256` is:

```
<METHOD>\n<PATH-WITH-QUERY>\n<TS>\n<BODY-SHA256-HEX>
```

Rules — strict, lowercase where indicated:

1. `METHOD` is the HTTP method in upper case (`GET`, `POST`, `DELETE`, …).
2. `PATH-WITH-QUERY` is the request path including a leading `/`, plus the query string if any. Query parameters are sorted lexicographically by key. Keys and values are URL-encoded per RFC 3986. Empty query → just the path, no trailing `?`.
3. `TS` is the same value as the header's `ts` field, as a decimal integer.
4. `BODY-SHA256-HEX` is the lowercase hex SHA-256 of the raw request body bytes. For an empty body, use the SHA-256 of the empty string (`e3b0c442…b855`).
5. `\n` is a single LF byte (`0x0a`). No trailing newline at the end.

Worked example (`POST /v1/device/register` with empty query and a JSON body `{"serial":"ABC"}`):

```
POST
/v1/device/register
1716290000
4ab5335fc428dd5acb18e99a9c531408017a472feb6fc5ce1e382723678083e8
```

### Clock skew

The backend accepts requests where `|server-now − ts| ≤ 300s` (±5 minutes). Outside that window returns `401 expired_token`. Devices NTP-sync on boot; firmware should refuse to make HMAC calls until NTP succeeds.

### Secret provisioning

A per-device 32-byte secret is generated by the backend during pre-provisioning. The factory burns `device_id`, `serial` and `secret` into the device's NVS partition before shipping. The backend stores the secret in `device_secrets.secret` (BYTEA). It must be available in cleartext to verify HMACs — encrypt-at-rest is enforced at the database/storage layer (phase 6 will add app-layer KEK encryption).

Secret rotation is supported by writing a new row and serving both old and new during a brief overlap window; details in phase 6.

## Users — JWT Bearer

### Access token

- **Algorithm**: `HS256` (HMAC-SHA256) over a single backend secret loaded from `JWT_SIGNING_KEY`.
- **TTL**: 15 minutes.
- **Claims**: `sub` (user UUID), `iat`, `exp`, `jti` (UUID v4, per-token).
- The signing key is symmetric. EdDSA / Ed25519 may be revisited if/when token verification is federated to other services (not planned for v1).

### Refresh token

- Opaque random string: **32 bytes**, base64url-encoded (no padding).
- Stored server-side as **SHA-256(token)** hex in `refresh_tokens.token_hash` (UNIQUE, indexed). The plaintext is never persisted. Argon2id is not used here — refresh tokens are high-entropy random values, so a fast cryptographic hash is both sufficient and necessary (Argon2 hashes are non-deterministic and cannot be indexed).
- **TTL**: 30 days from issuance.
- Single-use: every successful `/v1/users/refresh` issues a brand-new refresh token and marks the previous one as `used`.

### Rotation

Using a refresh token returns a new access/refresh pair and marks the previous refresh row as `used` (timestamped). Reusing an already-used refresh token is a strong signal of compromise: the server revokes **all** of that user's currently-valid refresh tokens (cascade revoke) and returns `401 unauthorized`. The user has to log in again.

Logout (`DELETE /v1/users/refresh` — not in v0.1.0) will explicitly revoke the presented refresh token without cascading.

## Error responses

| Status | Code | When |
|---|---|---|
| 401 | `unauthorized` | Missing or malformed auth header |
| 401 | `invalid_signature` | HMAC verification failed |
| 401 | `expired_token` | JWT past `exp`, or HMAC `ts` outside skew window |
| 401 | `invalid_credentials` | Wrong email/password on login, or replayed/revoked refresh |
